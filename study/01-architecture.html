Cluster Architecture & kubectl

What each component does, where kubeadm puts its files, and the kubectl habits you need before anything else.

Control plane components

ComponentJobWhere (kubeadm)
kube-apiserverFront door of the cluster. The only component that talks to etcd. Authenticates, authorizes, admits, validates and persists every request.Static Pod, port 6443
etcdDistributed key-value store holding all cluster state. Back it up.Static Pod, client port 2379, peer port 2380
kube-schedulerWatches for Pods with no nodeName, filters and scores nodes, binds the Pod.Static Pod
kube-controller-managerRuns the reconciliation loops: Deployment, ReplicaSet, Job, Node, EndpointSlice, ServiceAccount, PV binder, ...Static Pod
cloud-controller-managerCloud-specific controllers (LoadBalancer Services, node lifecycle, routes).Only on cloud providers

Node components

  • kubelet: systemd service on every node. Registers the node, watches assigned Pods, calls the container runtime through the CRI, runs probes, reports status. Config: /var/lib/kubelet/config.yaml, identity: /etc/kubernetes/kubelet.conf.
  • Container runtime: containerd or CRI-O. Inspect with crictl ps -a, crictl logs <id>, crictl images.
  • kube-proxy: DaemonSet that programs iptables / IPVS / nftables rules so Service ClusterIPs reach backend Pods.
  • CNI plugin: gives each Pod an IP and wires the node network. Config in /etc/cni/net.d, binaries in /opt/cni/bin. Flannel, Calico, Cilium, Weave are CNI plugins. NetworkPolicy needs a plugin that enforces it (Calico, Cilium; not plain Flannel).
  • CoreDNS: Deployment in kube-system that serves cluster DNS. Config lives in the coredns ConfigMap.
Three extension interfaces to remember: CRI (runtime), CNI (network), CSI (storage).

Request flow in the API server

  1. Authentication: client certificates, bearer tokens, ServiceAccount tokens, OIDC.
  2. Authorization: RBAC (Role / ClusterRole bindings), Node, Webhook, ABAC.
  3. Admission control: mutating then validating plugins and webhooks (LimitRanger, ResourceQuota, PodSecurity, ...).
  4. Validation and persistence in etcd, then watchers (controllers, scheduler, kubelets) react.

Important paths on a kubeadm node

/etc/kubernetes/manifests/      # static Pods: kube-apiserver, etcd, scheduler, controller-manager
/etc/kubernetes/pki/            # CA, API server and client certificates (etcd certs in pki/etcd/)
/etc/kubernetes/admin.conf      # cluster-admin kubeconfig (copy to ~/.kube/config)
/etc/kubernetes/kubelet.conf    # kubelet's kubeconfig
/var/lib/kubelet/config.yaml    # KubeletConfiguration (staticPodPath, cgroupDriver, ...)
/var/lib/etcd/                  # etcd data directory (hostPath of the etcd static Pod)
/etc/cni/net.d/                 # CNI configuration
/var/log/pods/  /var/log/containers/   # container logs on the node
journalctl -u kubelet           # kubelet logs

Objects, namespaces and the API

  • Every object has apiVersion, kind, metadata, usually spec (desired) and status (observed).
  • API groups: v1 (core: Pod, Service, ConfigMap, Secret, PV, PVC, Namespace, Node), apps/v1 (Deployment, ReplicaSet, StatefulSet, DaemonSet), batch/v1 (Job, CronJob), networking.k8s.io/v1 (Ingress, NetworkPolicy), rbac.authorization.k8s.io/v1, storage.k8s.io/v1.
  • Namespaced: Pods, Deployments, Services, ConfigMaps, Secrets, PVCs, Roles. Cluster-scoped: Nodes, Namespaces, PVs, StorageClasses, ClusterRoles, CRDs.
  • Labels select (-l app=web, Service and Deployment selectors). Annotations carry metadata and are never used for selection.
kubectl api-resources                      # kinds, short names, api group, namespaced?
kubectl api-resources --namespaced=false
kubectl api-versions
kubectl explain deployment.spec.strategy --recursive
kubectl get pod web -o yaml | less

kubectl and kubeconfig essentials

kubectl config get-contexts
kubectl config use-context cluster-2
kubectl config set-context --current --namespace=team-a   # do this first in every task
kubectl config view --minify                              # current context only
kubectl cluster-info
kubectl get nodes -o wide
kubectl get all -n kube-system

A kubeconfig has clusters (server URL + CA), users (cert, token) and contexts (cluster + user + namespace). KUBECONFIG=a:b kubectl config view --flatten merges files.

Useful output formats

kubectl get pods -o wide                 # node, IP
kubectl get pods -o name                 # pod/web-1
kubectl get pods -o jsonpath='{.items[*].metadata.name}'
kubectl get pods -o custom-columns=NAME:.metadata.name,NODE:.spec.nodeName
kubectl get pods --sort-by=.metadata.creationTimestamp
kubectl get pods -A --field-selector status.phase!=Running
kubectl get pods --show-labels -l 'env in (prod,staging)'
