PV and PVC

  • PersistentVolume (cluster-scoped): a piece of storage, created by an admin (static) or by a provisioner (dynamic).
  • PersistentVolumeClaim (namespaced): a request for storage. Pods mount PVCs, never PVs.
  • Binding is one-to-one. A PVC binds to a PV when: capacity ≥ request, requested access modes are offered, storageClassName matches, optional selector matches. A 1Gi claim can bind a 5Gi PV; the extra space is "wasted".
apiVersion: v1
kind: PersistentVolume
metadata: { name: pv-data }
spec:
  capacity: { storage: 5Gi }
  accessModes: [ReadWriteOnce]
  persistentVolumeReclaimPolicy: Retain      # Retain | Delete (| Recycle, deprecated)
  storageClassName: manual
  hostPath: { path: /mnt/data }              # or nfs:, csi:, ...
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: data-pvc }
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: manual                   # "" = no dynamic provisioning, omitted = default class
  resources: { requests: { storage: 1Gi } }
---
apiVersion: v1
kind: Pod
metadata: { name: app }
spec:
  containers:
    - name: app
      image: nginx
      volumeMounts: [{ name: data, mountPath: /usr/share/nginx/html }]
  volumes:
    - name: data
      persistentVolumeClaim: { claimName: data-pvc }

ReadWriteOncePodRWOPRead-write by a single Pod

PV phases and reclaim policies

  • Phases: Available → Bound → Released (claim deleted, data kept) → Failed.
  • Retain: PV stays Released with data; to reuse, edit the PV and delete spec.claimRef.
  • Delete: PV and backing storage removed with the PVC (default for dynamic provisioning).
  • A PVC in use by a Pod is protected from deletion (finalizer kubernetes.io/pvc-protection) until the Pod goes away.

StorageClass and dynamic provisioning

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
provisioner: ebs.csi.aws.com            # rancher.io/local-path, kubernetes.io/no-provisioner ...
parameters: { type: gp3 }
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer # or Immediate
allowVolumeExpansion: true
  • WaitForFirstConsumer: the PVC stays Pending until a Pod uses it, so the volume is created in the Pod's zone. Not a bug.
  • kubernetes.io/no-provisioner is used for local volumes with pre-created PVs and nodeAffinity.
  • Expansion: class must have allowVolumeExpansion: true and the driver must support it. Edit spec.resources.requests.storage on the PVC. Shrinking is impossible.
kubectl get sc
kubectl get pv,pvc -A
kubectl describe pvc data-pvc            # events explain Pending
kubectl get pv --sort-by=.spec.capacity.storage
kubectl patch pv pv-data -p '{"spec":{"claimRef":null}}'     # make a Released PV Available again

Mount options worth knowing

volumeMounts:
  - name: config
    mountPath: /etc/nginx/nginx.conf
    subPath: nginx.conf        # single file, hides nothing else; no live updates
    readOnly: true
securityContext:
  fsGroup: 2000                # files in the volume owned by group 2000, writable by it

Troubleshooting checklist

  • PVC Pending: no PV matches (size, access mode, class name typo), no default StorageClass, provisioner Pod down, or WaitForFirstConsumer.
  • Pod stuck ContainerCreating with FailedMount: PVC not bound, RWO volume already attached to another node, NFS server unreachable, wrong path.
  • Permission denied inside the container: set fsGroup or runAsUser to match the volume ownership.
