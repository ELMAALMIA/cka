RBAC, ServiceAccounts & Security

Who can do what (RBAC), which identity a Pod uses (ServiceAccounts), and how to lock down a container (securityContext, Pod Security Standards). Related labs: 10, 13, 14.

RBAC model

  • Role (namespaced) and ClusterRole (cluster-wide) list rules: apiGroups, resources, verbs, optional resourceNames.
  • RoleBinding grants a Role or ClusterRole to subjects inside one namespace. ClusterRoleBinding grants a ClusterRole everywhere.
  • Subjects: User, Group, ServiceAccount. RBAC is purely additive; there are no deny rules.
  • roleRef is immutable; recreate the binding to change it.
CombinationEffect
Role + RoleBindingPermissions in that namespace
ClusterRole + RoleBindingClusterRole's rules, but only in the RoleBinding's namespace
ClusterRole + ClusterRoleBindingRules in all namespaces + cluster-scoped resources
kubectl create role pod-reader --verb=get,list,watch --resource=pods -n dev
kubectl create rolebinding pod-reader-bind --role=pod-reader --serviceaccount=dev:inspector -n dev
kubectl create clusterrole node-viewer --verb=get,list --resource=nodes
kubectl create clusterrolebinding node-viewer-bind --clusterrole=node-viewer --user=jane
kubectl create rolebinding dev-admin --clusterrole=admin --group=devs -n dev    # built-in roles: view, edit, admin, cluster-admin

kubectl auth can-i list pods -n dev --as=jane
kubectl auth can-i list pods -n dev --as=system:serviceaccount:dev:inspector
kubectl auth can-i --list -n dev --as=system:serviceaccount:dev:inspector
kubectl auth whoami
kubectl describe rolebinding -n dev
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: deployer, namespace: dev }
rules:
  - apiGroups: ["apps"]                      # "" = core group (pods, services, secrets...)
    resources: ["deployments", "deployments/scale"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
  - apiGroups: [""]
    resources: ["pods/log"]                  # subresource
    verbs: ["get"]
  - apiGroups: [""]
    resources: ["configmaps"]
    resourceNames: ["app-config"]            # only this object
    verbs: ["get", "update"]

ServiceAccounts

  • Every namespace has a default ServiceAccount; Pods use it unless serviceAccountName is set. It has no RBAC permissions by default.
  • Tokens are short-lived and projected into /var/run/secrets/kubernetes.io/serviceaccount/ (token, ca.crt, namespace). No more auto-created token Secrets since 1.24.
  • automountServiceAccountToken: false on the SA or Pod when the app does not need the API.
kubectl create serviceaccount inspector -n dev
kubectl set serviceaccount deployment/web inspector -n dev      # edits the Pod template, triggers rollout
kubectl create token inspector -n dev --duration=1h
kubectl get deploy web -o jsonpath='{.spec.template.spec.serviceAccountName}'
Lab 13 lesson: a Running Pod can still be failing every API call with Forbidden. Read the logs, compare the permissions of each ServiceAccount with auth can-i, and change only what the task allows.

securityContext

spec:
  securityContext:                 # Pod level: applies to all containers
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000                  # group owner of mounted volumes
    runAsNonRoot: true
    seccompProfile: { type: RuntimeDefault }
  containers:
    - name: app
      image: nginx
      securityContext:             # container level: overrides Pod level
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        privileged: false
        capabilities:
          drop: ["ALL"]
          add: ["NET_BIND_SERVICE"]      # container level only, no CAP_ prefix
kubectl exec app -- id                         # check uid/gid
kubectl exec app -- grep Cap /proc/1/status    # capability bitmasks

Pod Security Standards (admission)

  • Levels: privileged (no limits), baseline (blocks known escalations: hostNetwork, privileged, hostPath...), restricted (non-root, drop ALL, seccomp, no privilege escalation).
  • Modes per namespace label: enforce (reject), audit (log), warn (kubectl warning).
kubectl label ns prod pod-security.kubernetes.io/enforce=restricted \
                      pod-security.kubernetes.io/warn=restricted

Users and certificates (CKA)

openssl genrsa -out jane.key 2048
openssl req -new -key jane.key -subj "/CN=jane/O=devs" -out jane.csr
cat <<EOF | kubectl apply -f -
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata: { name: jane }
spec:
  request: $(base64 -w0 jane.csr)
  signerName: kubernetes.io/kube-apiserver-client
  usages: ["client auth"]
  expirationSeconds: 86400
EOF
kubectl certificate approve jane
kubectl get csr jane -o jsonpath='{.status.certificate}' | base64 -d > jane.crt
kubectl config set-credentials jane --client-certificate=jane.crt --client-key=jane.key --embed-certs
kubectl config set-context jane@k8s --cluster=kubernetes --user=jane

The certificate's CN becomes the username and O the group. Inspect any certificate with openssl x509 -in file.crt -noout -text.

Other security topics

  • Admission controllers: enabled with --enable-admission-plugins on the kube-apiserver (NodeRestriction, LimitRanger, ResourceQuota, PodSecurity...). Webhooks: MutatingWebhookConfiguration, ValidatingWebhookConfiguration, ValidatingAdmissionPolicy (CEL).
  • Secrets encryption at rest: EncryptionConfiguration passed with --encryption-provider-config.
  • Image pull secrets and image policy: prefer pinned tags or digests.
